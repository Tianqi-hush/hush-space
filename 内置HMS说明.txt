内置 HMS Core 说明
==================

本源码包为了控制体积，没有包含 assets 下的两个 APK（共约 66MB）：
  app/src/main/assets/hms/hmscore.apk                   约 54MB
  app/src/main/assets/hms/kits/AccountKit-base.apk      约 9.5MB

要恢复完整可构建状态：
1. 新建目录 app/src/main/assets/hms/ 和 app/src/main/assets/hms/kits/
2. 放入官方 HMS Core APK，重命名为 hmscore.apk
3. 从 hmscore.apk 里取出账号 kit：
     unzip -j assets/hms/hmscore.apk assets/kits/AccountKit-base.apk \
       -d app/src/main/assets/hms/kits/

HMS Core 本体：
  包名      com.huawei.hwid
  版本      6.16.4.362
  versionCode 61604362
  MD5       b9ee947aae0f3f2c945b5a254dd4aea2
  大小      56,701,278 字节
  签名      CN=China, OU=Huawei, O=Huawei, L=Shenzhen, ST=Shenzhen, C=CN
            SHA-256 e49d5c2c0e11b3b1b96ca56c6de2a14ec7dab5ccc3b5f300d03e5b4dba44f539

账号 kit（华为账号登录界面，必须和本体一起内置）：
  包名      com.huawei.hms.account
  版本      6.22.0.301
  versionCode 62200301
  MD5       f55f1426bcfd433ee83e13782b8321bb
  大小      9,549,431 字节

为什么必须带 kit
----------------
HMS Core 6.16 把账号界面拆成了独立 APK，启动时先问
FeatureInstallManager.getAllInstalledModules() 里有没有 HwID_Features：
  - 有 → 直接进账号界面；
  - 没有 → 从 assets 解压 kit，再走 PackageInstaller 安装。
容器里没有 INSTALL_PACKAGES 权限，第二步必然失败（日志：
FeaturesLoadingActivity installFail errorcode:2），表现就是登录页一直转圈。

2.6.12 起做了两层兜底：
1. 给 com.huawei.hwid 的 ApplicationInfo.metaData 注入
   com.android.dynamic.apk.fused.modules=HwID_Features，
   让 getAllInstalledModules() 直接认「已装」，跳过安装；
2. 安装 HMS Core 时把 AccountKit-base.apk 一并装进空间，
   老版本空间在宿主启动时后台补装。

2.6.13 起补上「调用方包名」：
HMS 的 ForegroundBus 会拿 Activity.getCallingPackage() 跟请求里的
cpPackageName 比对，不一致直接返回 907135000，账号页弹「无法获取数据」。
容器里所有 guest 都跑在宿主进程里，系统只会把 launchedFromPackage 填成
com.hush.space，所以容器在 guest 调 startActivity 时记下真实虚拟包名，
Activity 创建前写回 ActivityClientRecord.launchedFromPackage。
日志确认点：diag.log 里出现
  caller: launchedFromPackage=com.huawei.appmarket

2.6.14 起把调用方包名改到 Instrumentation：
Android 12+ 的 LaunchActivityItem 在 ActivityClientRecord 建好之前就执行，
上一版在 EXECUTE_TRANSACTION 里改 record 拿不到（日志：record 未找到）。
现在在 AppInstrumentation.callActivityOnCreate 之前写 Activity 的
mLaunchedFromPackage 字段，onCreate 里 getCallingPackage() 就能拿到正确值。

2.6.15 修「HMS 每秒崩一次」：
HMS 的 kit 容器服务（IKitContainerServiceManager）跨进程调用时，
服务端用 AttributionSource.enforceCallingUid() 校验「声明 uid == 调用 uid」。
容器里所有 guest 共用宿主真实 Linux uid（10442），但 ContextCompat.fix()
把 app Context 的 attribution uid 写成了虚拟 uid（10001），于是每次都抛
  SecurityException: Calling uid: 10442 doesn't match source uid: 10001
:core 进程起来即死，账号、应用市场、游戏全调用不到 HMS。
现在 attribution uid 统一用宿主真实 uid，和包名（宿主包名）、Binder 内核 uid
三者一致。同版本还修了两处：
  - 没有 LAUNCHER activity 的包（HMS Core / 账号 kit）在首次绑定进程时
    会把 null 存进 stub intent，下一轮 LaunchActivityItem.hashCode()
    对 null mIntent 抛 NPE 打死进程 —— 现在用当前 intent 兜底；
  - getPackageInfo(pkg, GET_ACTIVITIES) 生成失败时不再返回 null
    （HMS 自检会当成「没装」），去掉组件数组再生成一次，并记录真实异常。

缺少这两个文件时应用仍可正常编译运行，只是设置页的「华为 HMS Core」
开关会提示「内置安装包缺失」。

2.6.16 修「账号 kit 进程起不来 / 调用方仍然对不上」：
1. AccountKit-base.apk 的清单里 <application android:name=
   "com.huawei.hwid.common.app.HwIDApplication">，这个类在 hmscore.apk
   里，不在 kit 自己的 dex 里。kit 被当成独立包安装后，进程一起来
   LoadedApk 就 ClassNotFoundException -> Unable to instantiate
   application，com.huawei.hms.account.core 永远起不来。
   现在给 kit 包的 ApplicationInfo.className 统一换成 android.app.Application。
2. 真机上 HMS Core 与账号 kit 是同一个 APK 的 base + split，共用一个
   ClassLoader；容器里它们是两个独立包。kit 里的 HwIDProvider 静态初始化
   要 com.huawei.hms.support.log.KitLog（只在 hmscore.apk 里），所以
   Provider 装不上、账号服务拿不到数据。现在绑定进程时用
   BaseDexClassLoader.addDexPath() 把对方的 base.apk 追加进当前 ClassLoader，
   双向补齐（hwid ↔ com.huawei.hms.*）。
3. 调用方包名不再依赖 Activity.mLaunchedFromPackage（Android 17 上这个
   字段已经不存在，日志：NoSuchFieldException）。改成：
    - 事务执行前直接写 LaunchActivityItem 的 launchedFromPackage；
    - 同时按「值等于宿主包名」扫描 LaunchActivityItem / ActivityInfo /
      Activity 的 String 字段并替换，ROM 改字段名也能命中；
    - onCreate 前回读 getCallingPackage() 写日志确认。
4. PackageInfo 生成时单个组件解析失败只跳过该组件，不再整包返回 null
   （HMS 自检会当成没装）。
5. HMS Core / 账号 kit 不再套用「连续崩溃就按加固壳跑 ART hook」的重试，
   也不再加载 Xposed 模块 —— 这两件事都会改账号 SDK 内部方法。

2.6.17 修「调用方包名怎么改都还是 com.hush.space」：
这次从 HMS 日志里把链路彻底对上了 —— Android 17（SDK 37）的
Activity.getCallingPackage() 已经不走 ActivityTaskManager 了，而是

    Activity.getCallingPackage()
      -> ActivityClient.getInstance().getCallingPackage(mToken)
        -> IActivityClientController.getCallingPackage(token)   // Binder

Activity 里既没有 mLaunchedFromPackage 字段（2.6.14 的 NoSuchFieldException），
ActivityClientRecord 里也没有这个字段了，全被挪到 system_server 的
ActivityRecord 里，客户端只有拿 token 去问这一条路。所以之前写字段、
写 LaunchActivityItem、hook ATM 的 getLaunchedFromPackage 全都读不到。

现在在 guest 进程里把 IActivityClientController 换成动态代理：
- 只拦 getCallingPackage / getLaunchedFromPackage；
- token 命中「启动时记录的虚拟调用方」就返回它，其余方法原样透传；
- 两条安装路径：hook IActivityTaskManager.getActivityClientController()，
  以及直接 ActivityClient.setActivityClientController(proxy) 预置缓存，
  防止被 ActivityThread 重新取服务时覆盖；
- token 对不上（PendingIntent / 系统转发）时，3 秒内最近一次记录的调用方兜底。

日志里应该看到：
  caller: ActivityClient 控制器已接管
  caller: getCallingPackage -> com.huawei.appmarket token=...
HMS 自己那行会变成：
  StartUpGuideLoginActivity: onCreate mCallingPackageName = com.huawei.appmarket

2.6.18 修「调用方能过、但登录还是失败 / HMS Core 点不开」：
1. 2.6.17 的 ActivityClient 控制器接管生效了 —— 2.6.18 前的日志里
   Different calling package / 907135000 已经消失，卡点后移了一层：
     ForegroundBus: Failed to get resolveInfo
     ForegroundBus: errorReturn code:907135001,
                    msg:action configure is invalid:com.huawei.hms.hwidjos.signIn
   HMS 的 RuleEngine 会把 com.huawei.hms.account.signIn 改写成
   com.huawei.hms.hwidjos.signIn（游戏/渠道包走这条），而这条 action
   只声明在 GameServiceKit.apk 里（kit 名 hwidjos，包名
   com.huawei.hms.game）。之前只内置了 AccountKit，所以游戏登录必然失败。
   现在 GameServiceKit.apk 一起内置、一起装进空间；补装后重启 HMS Core
   进程（它只在启动时扫一遍 kit，不重启就永远看不到新装的 hwidjos）。
2. HMS Core 6.16 的清单里没有 LAUNCHER activity（真机上它是从「设置 →
   华为账号」进的，没有桌面图标）。容器里点图标走
   getLaunchIntentForPackage，以前直接返回 null → 点了没反应。
   现在给一个入口：账号 kit 的 StartUpGuideLoginActivity，
   并把调用方写成 com.huawei.hwid（从 HMS 自己进去的语义）。
3. kit 包的 Application 一律退化成 android.app.Application。
   GameServiceKit 的 JosApplication 虽然在自己的 dex 里，但真机上它是
   split、跟 CoreApplication 同进程；容器里当独立包跑会缺上下文。
4. fused.modules（HwID_Features）除了给 com.huawei.hwid 补，也给 kit 包补。
   日志里 FeatureManager: featrues:[] 说明它读的是 kit 自己那份。

2.6.19 修「2.6.18 装了 GameServiceKit 还是 907135001」+ 日志丢失：
1. 2.6.18 给所有 kit 包注入的 fused module 名一律是 HwID_Features，
   这是错的。FeatureInfoManager 的判定是
     fused.modules.split(",") + PackageInfo.splitNames
     -> 去掉 config.*
     -> 调用方拿 kit_name.split(";") 做 containsAll
   game kit 的 kit_name 是 core;game;payjos;hwidjos;iapjos;jos，
   必须逐字出现这些名字才算「已装」。现在按包分别注入：
     com.huawei.hwid        -> HwID_Features
     com.huawei.hms.account -> hwid,account
     com.huawei.hms.game    -> core,game,payjos,hwidjos,iapjos,jos
   名字对不上时 FeatureManager 不会调用 HwidJosMainEntry.onCreated，
   hwidjos.signIn 就一直没注册，游戏登录固定报 907135001。
2. HMS Core 把 kit 列表读进内存后不再刷新。升级到本版后第一次启动，
   无条件杀一次 com.huawei.hwid + com.huawei.hms.account 两个进程，
   强制下次拉起时重扫（每个宿主进程只做一次）。
3. 日志丢失：2.6.15 之后拿回来的 diag.log 一直停在 2.6.14。
   - guest 进程 Diag.init 时 HushCore.getContext() 可能还是 null，
     以前直接 return，整个进程一行都不写；现在退回反射再取一次。
   - 路径统一成宿主包名拼的 Android/data/com.hush.space/files/diag.log，
     guest 不再写自己那个包的目录（那个目录导出时根本没人翻）。
   - 轮转阈值 4MB -> 16MB，避免用户只拷 diag.log、内容却在 .prev 里。
4. 打开 HMS Core 图标的日志改成进 diag（pm: HMS 无 launcher，入口=...）。

2.6.20 修「点 HMS 图标进去 1-2 秒闪退」：
2.6.18/2.6.19 把入口指向账号 kit 的 StartUpGuideLoginActivity，
那是「登录引导页」——从 HMS 自己进来时它判断不需要引导就直接
finish，表现出来的就是界面闪一下就没了。
改回真机上「设置 → 华为账号」的那个页面：
  com.huawei.hwid.cloudsettings.ui.HuaweiIDForSettingsActivity
（hmscore 本体，进程 com.huawei.hwid.container2，清单里声明了
 com.android.settings.action.IA_SETTINGS），调用方仍然写
com.huawei.hwid，保证 ForegroundBus 校验能过。

2.6.21 修「打开 HMS 界面 1-2 秒后闪退」的真正原因：
和入口页面无关。2.6.20 的 diag.log 里能看到完整的作案时间线：
  09:07:33.017  点图标，拉起 com.huawei.hwid.container2
  09:07:33.441  [com.hush.space] hms: 重启 HMS 进程（升级后重扫 kit）
  09:07:33.442  [com.hush.space] hms: 启动补装账号 kit uid=0 -> true
  09:07:34.x    hwid 各进程重新绑定，账号页起来
宿主冷启动 3 秒后，后台补装线程跑 ensureKits()，判定本版本还没
「重扫」过，于是调 restartHms() 把 com.huawei.hwid + com.huawei.hms.account
全杀了——正好落在用户点开华为账号的那两秒里，界面当然一闪就没，
而且日志里一条异常都没有（不是崩溃，是被自己人 kill 的）。
改动：
1. restartHms() 先查 BProcessManagerService 里 HMS / 账号 kit 还有没有
   活着的 pid。有就跳过，只写一行
     hms: HMS 进程存活，跳过重启（...），kit 下次冷启动生效
   kit 已经落盘，HMS 下次冷启动 CoreApplication 必然重新扫到，没必要
   为一份内存里的 kit 列表打断正在进行的登录。
2. ensureHmsKitsAsync() 只在宿主主进程跑。SpaceApplication 在每个
   com.hush.space:pN 里都会 onCreate，以前 8 个进程各解析一遍 9.5MB 的
   kit 包，也让「补装即重启」在任何时刻都可能触发。进程名读不到时保持
   旧行为，宁可多跑一次也不漏装。

2.6.21 修 com.huawei.hwid.persistent 起不来（CoreApplication 崩）：
2.6.20 日志：
  bind: handleBindApplication FAILED at start
  Caused by: Can't create handler inside thread Thread[binder:32130_3]
             that has not called Looper.prepare()
    at com.huawei.hms.app.CoreApplication.attachBaseContext(CoreApplication.java:188)
com.huawei.hwid.persistent 是被 provider 拉起的，绑定入口在
IBActivityThread.acquireContentProviderClient，跑在 binder 线程池里。
HMS 的 CoreApplication.attachBaseContext 第一件事就是 new Handler()，
binder 线程没有 Looper 直接抛，Application 建不出来，进程废掉。
改动：handleBindApplication 里 makeApplication / Application.onCreate
两步统一走 callOnGuestMain()：当前线程是主线程就原地执行（老路径不变），
是 binder 线程就 post 到主线程并同步等结果；主线程 6 秒没响应（还没进
Looper.loop 的极端情况）就回退到本线程并补一个 Looper，任务带 CAS 保护，
不会出现两个 Application 实例。

2.6.21 新增诊断：
AppInstrumentation 记录 Activity 的 create/resume/pause/destroy，
带真实类名和 intent（act: create com.xxx.Yyy cmp=... act=...）。
HMS 的 kit 有一层 runtimekit 代理（清单里是
com.huawei.hms.runtimekit.stubexplicit.*，运行时才换成 kit 里的真实类），
以后再遇到「闪退」，看 act 行就能分清是代理没换成还是真实类自己 finish。

2.6.23 分析 2.6.22 日志：华为应用市场登录卡在「正在登录…」
这次用户测的是应用市场，链路和光遇不同：
  09:49:41.314  BridgeActivity(appmarket) pause
  09:49:41.318  AccountSignInHubActivity(appmarket) create/resume，49ms 后 pause
  09:49:41.374  BridgeActivity(appmarket) create/resume，15ms 后 pause
  09:49:41.410  UiJumpActivity(hwid) create/resume
  09:49:41.431  UiJumpActivity 调 getCallingPackage -> com.huawei.appmarket
  09:49:41.439  UiJumpActivity pause
  09:49:41.443  ActivityResultItem 回到 appmarket
  09:49:41.460/472/485  三层依次 destroy finishing=true
  09:49:52.385  appmarket 放弃，界面停在「正在登录…」
UiJumpActivity 是 1x1 透明的跳板页，正常行为是：onCreate 里按
intent.extra.hms.core.DELEGATE_NAME 找到 delegate（名字是
com.huawei.hms.core.activity.ForegroundBus，真实类 com.huawei.hms.core.activity.b），
交给它去请求 hwid.core 的 HMSCoreService 拉起真正的账号页。
反编译确认 e() 只在两种情况下返回 false 并 setResult(1)+finish：
  a) DELEGATE_NAME 为空；
  b) delegate 类 newInstance 失败。
两种情况都属于「参数没到」或「单例没初始化」，而这两种正好都是拆包容器
最容易出的问题。以前日志里只有 cmp/act/flags，看不到 extras，无法判定。

2.6.23 新增诊断（都是纯日志，不改行为）：
1. act: <阶段> <类名> cmp=... act=... flags=... extras={k=v, ...}
   intent 的 extras 全部摊平，Bundle/Intent 只打 key 和组件。
2. act: start from=<发起方> req=<requestCode> cmp=... act=... extras=...
   每次 startActivity（限华为系包）记下发起方和参数，能看出参数在哪一跳丢的。
3. act: post-create <类名> finishing=true/false
   onCreate 一返回就看是不是已经准备退出，true 的还带上当时的栈。
4. svc: bindService -> true/false <包名>
   svc: onServiceConnected <组件> binder=true/false dead=false
   绑定到底成没成、服务有没有连上，以前只有一行 bindService 请求，没有结果。

2.6.23 顺带缩短 HMS 冷启动等待：
2.6.22 日志里 com.huawei.hwid.core 从 09:49:33.327 起来，到 09:49:46.398
才完成 Application 绑定，用了 13 秒；其中 p6 打了
  bind: Application.onCreate 主线程 6s 未执行，回退当前线程
这条等待是 2.6.21 为 binder 线程绑定 Application 加的兜底，超时值 6 秒太长，
刚好把 UiJumpActivity 的请求拖到服务未就绪的时候。改成 1.2 秒——主线程正常
几十毫秒就进 Looper，1.2 秒足够，真等到 1.2 秒说明主线程确实没起来，回退
本线程补 Looper 也不会更差。

2.6.23 追加：跳板页自检
UiJumpActivity 起来时会先跑一遍「同样的查找」并把结果打出来：
  act: probe UiJump delegateName='...' center=true instance=com.huawei.hms.core.activity.b
如果 delegateName 是 <null>，就是参数没传过来；如果是 instance=NULL，
后面会跟一段异常栈，直接告诉我们 ForegroundBus 为什么建不起来。

2.6.24 找到「点开 HMS Core 一秒退回桌面」的真正原因：七个基础框架 kit 从来没装过。

证据（2.6.23 日志，三条独立线索指向同一件事）：
1. 直接报错：
   Caused by: java.lang.ClassNotFoundException:
     Didn't find class "com.huawei.hwid.fingerprint.provider.HwIDFileProvider"
     on path: DexPathList[[account/base.apk, hwid/base.apk]]
   Suppressed: java.lang.NoClassDefFoundError:
     Failed resolution of: Lcom/huawei/hms/runtimekit/container/kitsdk/KitFileProvider;
   KitFileProvider 在 Framework-runtime.apk 里，没装 → 父类解析不了 → provider 全废。
2. HMS 主动去找，全部返回 null：
   pm: getPackageInfo pkg=com.huawei.hms.commonkit -> null
   pm: getPackageInfo pkg=com.huawei.hms.kitstore   -> null
3. 登录链路那个跳板页
   com.huawei.hms.runtimekit.stub.HMSKitStandardC2NEStubActivity1
   的类只在 Framework-runtime.apk 的 dex 里。反编译确认：
     只有 Framework-runtime 命中 HMSKitStandardC2NEStubActivity1；
     hmscore / AccountKit / GameServiceKit 三个包全部未命中。
   所以跳板页起来的是个空壳，onCreate 里没东西可做，立刻 finish，
   整条 Activity 栈跟着退掉 —— 用户看到的就是「进界面 1-2 秒闪退」，
   而且没有异常（finish 是正常调用，不是崩溃）。

依据是 hmscore.apk 自带的 assets/raw/kits_config.json，里面有一份
priority_install：
   Framework-common, Framework-manager, Framework-runtime, Framework-ui,
   Framework-privacy, Framework-kitstore, Framework-webapp
真机上这七个是 HMS Core 安装完自己从 assets 解压装的。容器里 kit 是我们
手工装的，只装了 AccountKit + GameServiceKit，这七个一个都没有。

2.6.24 改动：
1. 内置七个 Framework kit（从 hmscore.apk 的 assets/kits/ 原样取出）：
     com.huawei.hms.commonkit   Framework-common.apk    fwcom-grs,fwcom-util,measurement,apptouch
     com.huawei.hms.fwkit       Framework-manager.apk   kpms,kams
     com.huawei.hms.runtimekit  Framework-runtime.apk   runtime
     com.huawei.hms.fwui        Framework-ui.apk        fwui
     com.huawei.hms.privacy     Framework-privacy.apk   privacykit
     com.huawei.hms.kitstore    Framework-kitstore.apk  kitstore
     com.huawei.hms.webapp      Framework-webapp.apk    webapp-runtime
   模块名严格照 kits_config.json 的 kit_name 写：FeatureInfoManager 用

== 2.6.36 ==
2.6.35 装上了，Toast 说「华为账号加载失败：找不到 KitLoaderManager」。
这句话直接指出了我的一个硬 bug，不是 HMS 的问题。

【为什么找不到 KitLoaderManager】
KitLoaderManager 在 Framework-runtime.apk 里，由 runtimekit 自己的
DexClassLoader 加载。我之前写的是：
    Class.forName("com.huawei.hms.runtimekit.kitloader.KitLoaderManager")
只有一个参数的 Class.forName 用「调用方所在的 ClassLoader」，也就是宿主
com.hush.space 的 PathClassLoader。那个 CL 里只有宿主自己的 dex，
永远看不到 Framework-runtime 里的类 —— 所以必然 ClassNotFoundException，
我把它 catch 成 null，于是报「找不到」。

反编译确认类是真的存在，签名也对：
    Lcom/huawei/hms/runtimekit/kitloader/KitLoaderManager;
    public static getInstance(Landroid/content/Context;)L...KitLoaderManager;
    public loadKit(Landroid/os/Bundle;Z)Z
    public inject(Ljava/lang/String;LE/d;)Z
    static 字段 f 就是单例缓存
ContainerActivity 自己也是调 getInstance(this)，没有别的入口。

改动：Class.forName(name, false, cl) 依次尝试
    ① 跳板页自己的 ClassLoader（a.getClass().getClassLoader()）
       —— ContainerActivity 和 KitLoaderManager 同在 Framework-runtime.apk，
          这个 CL 必然能加载，而且拿到的 f 就是 HMS 用过的那个实例，
          loadKit 的缓存因此共享；
    ② 线程上下文 CL；
    ③ 宿主 CL（兜底）。
并且 getInstance 传的是 Activity 本身，不是 Application，和 HMS 完全对齐。

【顺带纠正一个误判】
2.6.33 撤掉 prewarm 的理由是「日志证明预热无效」。现在看，那是因为
prewarm 内部调的就是这个坏掉的 kitLoader，它从来没拿到过 KitLoaderManager，
等于什么都没做。所以「预热无效」这个结论是错的。
2.6.36 恢复 prewarm 调用，放在 super.callActivityOnCreate 之前：
先改对 session 里的 apk_path / native_path / kit_app_class，再 loadKit 一次，
HMS 自己的 loadKitForActivity 随后就会命中缓存直接成功。
prewarm 全程 try-catch，不 finish、不 startActivity，不碰生命周期
（2.6.28 的 SuperNotCalledException 是 return 掉 super.onCreate 造成的，
这次没有这个问题）。

== 2.6.40 ==
2.6.39 只做取证，没有改行为。这一版把「协议页显示无网络」真正按容器和真机的
差异修掉，根因不是手机没网，而是 HMS 的 split 语义在容器里只恢复了一半。

【为什么框架不适配 HMS Core】
HMS Core 6.x 不是一个普通 APK，而是一个「base + 一堆 kit」的动态模块体系：
  - 真机上 kit 是 split，全部跑在 com.huawei.hwid 的进程里；
  - 所有 split 共用同一个 ClassLoader、同一个 Application；
  - 所有 split 共用同一个 AssetManager / Resources（资源表安装时合并过一次）；
  - 所有 split 共用同一个 dataDir，WebView 的 profile/cache 也在里面。
容器把每个 kit 当成独立安装的普通应用，2.6.24/2.6.25 只补了「dex 串成一条 +
ClassLoader 共用」，另外三样一直没补：
  1. assets / resources 仍是各看各的：hwid 进程里打开 account kit 的协议页，
     H5 的 file:///android_asset/... 在 hwid 的 AssetManager 里不存在；
  2. WebView 数据目录：VCore 只给 device-protected 目录建 app_webview，
     真正的 credential dataDir 下没有；
  3. 明文流量策略：宿主 targetSdk=28，WebView 默认禁止 http；HMS 的 H5 里
     混着明文资源，被拦后页面只会显示自己的「无网络」兜底页。
所以前面所有版本都在跟「kit 页面能不能起来」赛跑，起来之后必然卡在协议页。

【2.6.40 改动】
1. HmsKitCtx.shareAssets：HMS 进程绑定时，把其它 HMS 包（hwid + account +
   game + 七个 Framework kit）的 base.apk 追加进当前进程的 AssetManager。
   顺序在 hwid 本体之后，已有资源 ID 仍由本体优先解析，不会改现有页面。
   日志：kitctx 共享 assets com.huawei.hwid += com.huawei.hms.account cookie=…
2. HmsKitCtx.prepareWebViewDir：在 guest 的 credential dataDir 下补建

4. HmsKitCtx.preInstall：在 makeApplication 之前先用 packageContext 填好
   CoreApplication.e/f。CoreApplication.attachBaseContext 里初始化的
   NetworkUtil / Manager 单例不会再缓存 null；Application 建好后再换成
   Application 本身。
5. IConnectivityManagerProxy 在 binder 出口统一改写包名：kit 页面用的是

CarrierData 类 new 出来的。真机上 kit 页面和 hwid 共用一份 ClassLoader，
序列化再反序列化回来还是同一个 Class。

容器里的链路：
1. Intent 要经过我们的 ActivityStack 和真实 system_server 来回 Parcel；
2. 回到 guest 进程时，ActivityThread 用 **guest 的 ClassLoader** 反序列化
   （2.6.25 已把 kit 的 dex append 进去），于是 CarrierData 由 guest CL 定义；
3. runtimekit 给 kit 建的却是另一份 DexClassLoader（ClassLoaderManager
   newKitClassLoader 的父加载器是 ClassLoader.getSystemClassLoader()，
   在容器里就是宿主/system CL，不是 guest CL），OneKey 页面里的
   checkcast CarrierData 用的是 kit CL 那一份；
4. 两个 Class 不是同一个，checkcast 抛 ClassCastException，被 runtimekit
   的 V.d.getParcelableExtra 吞掉返回 null → C9 判定「无运营商数据」→ finish。

同样的 double-definition 问题也出现在 session 里的 kit_secure_intent
（kams 预存的 intent），所以只修 ClassLoader 还不够，那份 intent 也要丢。

【2.6.41 改动】StubLauncher（只改这一个文件）
1. prewarm 在 loadKit 成功、kit ClassLoader 建好之后调用 repairExtras()：
   把 intent 的 extras 先 writeBundle 到 Parcel，再用 kit 自己的
   getKitClassLoader(kit_uid) 读回来，再 replaceExtras。
   这样 CarrierData 等 Parcelable 变成 kit CL 里的那一份，checkcast 通过。
2. stripSecureIntent：mStubLoadInfo 里如果有 kit_secure_intent 直接删掉，
   让 ContainerActivity 用跳板页自己这份（已经修过的）intent。
3. describe() 的 stub{…} 增加 carrier= 字段，日志里可以直接看到 kit 页面
   实际拿到的 intent 里运营商数据在不在。
